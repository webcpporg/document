[#document-parsing]
== Parsing

`wd::parse(text, options)` is `JSON.parse(text)`: it reads JSON text into a new owned document and
returns it in a `result`. It accepts what RFC 8259 and `JSON.parse` accept, and nothing else: no
comments, no trailing commas, and whitespace of space, tab, line feed and carriage return only. A
key written twice keeps the last value in the first one's place, as JavaScript does. A
document's parser never throws: its input is the network's, and every failure is a value.

`wd::parse<Traits>` parses into a document of other traits, as `wd::parse<wd::js_traits>(text)`
does in <<document-numbers>>; `wd::parse_into(buffer, text)` parses into a buffer the program owns
(<<document-images>>); and `wd::parse_or_throw(text)`, with exceptions only, throws as
`JSON.parse` does (<<document-exceptions>>).

[#document-parsing-options]
=== Limits and revivers

`wd::parse_options` holds the limits of a parse, each of which is `errc::capacity` when it is
passed, and the revivers:

[cols="1,3",options="header"]
|===
| Member | What it is

| `max_depth`
| The deepest nesting of arrays and objects, 256 unless told otherwise.

| `max_bytes`
| The most bytes of text, every chunk counted; no limit unless told otherwise.

| `max_document_bytes`
| The largest image an owned document grows to, 64 MiB unless told otherwise.

| `revive_dates`
| Whether a string in exactly the format of `Date.prototype.toJSON` becomes a date
  (<<document-strings-dates>>).

| `revive_bytes`
| Whether text of the traits' bytes policy becomes bytes (<<document-strings-bytes>>).
|===

[#document-parsing-memory]
=== Memory per value

Every value of a document is a node of the image's tree, and a node takes 192 bytes of the image
whatever it holds: a number, `true`, `null`, an empty string, an empty array or object alike. A
string's bytes, and a key's, take a block of their own besides: 48 bytes for a string of 8 bytes,
112 for one of 100. So `"abcdefgh"` takes 240 bytes, and `{"k":0}`, an object and a member with
its key, 432. These are the image's sizes on every target, measured, as an image is the same
bytes everywhere (<<document-images>>).

A short value costs far more in the image than in its text. Measured, 2 MB of text, `+[0,0,...]+`
with 1,048,576 zeros, makes an image of 268 MB, 128 times the text, which `shrink_to_fit()`
brings to 201 MB; and while an owned image grows, its old and new buffers are held at once. So
the default `max_document_bytes` is 64 MiB, which refuses input from the network early: it is
reached by 700 KB of such text, which a native release build reads for 0.4 seconds with 137 MB
resident before it fails, where a limit of 1 GiB would take 11 MB of text, 9 seconds and 2.2 GB.
*A program that parses larger documents raises `max_document_bytes`* to what it can afford, and
sets `max_bytes` with it: a parse past either fails with `errc::capacity`. A document the program
builds itself, with `create`, keeps a limit of 1 GiB (<<document-images>>).

[#document-parsing-chunks]
=== In chunks

`wd::parser` is the parser itself, `wd::basic_parser<Traits, Storage>` for other traits or a
buffer of the program's: `write(chunk)` takes the text in chunks of any size, split anywhere,
inside a string, a number, an escape or a character's bytes, down to one byte at a time, and
`finish()` ends the text and returns the document. The document a parser builds is the one a
whole parse builds, however the text is split:

The parser builds the document node by node as each chunk arrives, so the document may grow and
its image move between two chunks; `finish` returns it. `reset()` makes the parser ready for
another text, its selectors kept (<<document-selectors>>).

[#document-parsing-errors]
=== Errors and offsets

Malformed text is `errc::syntax`, JavaScript's `SyntaxError`. `offset()` is the count of bytes
consumed, which after a syntax error is the offset where it was found, the same however the text
was split, and `cause()` is the code of Boost.JSON's parser behind it. A number the traits refuse
is `errc::range` (<<document-numbers-refused>>), and a limit passed `errc::capacity`.

A parser reads one text: anything but whitespace after it is `errc::syntax`, whose `cause()` is
Boost.JSON's `extra_data`, at the offset where the second text begins, whether it comes in the same
chunk or a later one, so `"1 2"` and `"[1] "` then `"[2]"` are refused, and no selector sees the
second text. A parser that failed stays failed: every later `write` and `finish` returns the same
error, until `reset`. A finished parser takes no more text, which is `errc::syntax`, until `reset`.
And `max_bytes` counts every chunk written, not each one alone:

[#document-parsing-surrogates]
=== Lone surrogates

`+JSON.parse('"\ud800"')+` gives a string holding a lone surrogate, half of a UTF-16 pair. document's
parser refuses it with `errc::syntax`, with either encoding, `utf16` included, which could store
it. That is a limit of Boost.JSON's parser, which document reads JSON with, and a deliberate
choice: the parser cannot deliver a lone surrogate, but only refuse it, or, with
`allow_invalid_utf16`, replace it with U+FFFD, which would change the text without a word. So it
is documented, not worked around. A program that must hold one, with `wd::utf16`, stores it with
`set` of a `std::u16string_view`, and `stringify` writes it as `JSON.stringify` does
(<<document-strings-encodings>>).
