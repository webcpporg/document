[#document-stringify]
== Writing JSON

`wd::stringify(v, indent)` is `JSON.stringify(v, null, indent)`, and writes its exact bytes: the
keys in the policy's order (<<document-order>>), strings escaped as `JSON.stringify` escapes them
(<<document-strings>>), numbers as JavaScript writes them (<<document-numbers>>), a date as
`Date.prototype.toJSON` writes it, and bytes by the traits' policy. It is a function of a handle
or of a document, and a member of both, `doc.stringify(2)` and `doc["user"].stringify()`:

[source]
----
include::{examples}/document_quick_start.cpp[tag=stringify,indent=0]
----

The indent is JavaScript's: 0 writes compactly, a larger one is clamped to 10 spaces, and an empty
array or object is written `[]` or `{}` at any indent. A value that is `undefined`, a handle of
nothing or a document that holds `undefined`, writes no text, as `JSON.stringify(undefined)`
returns none. `stringify` returns a `std::string`, in the standard allocator whatever the
document's, and keeps its stack there too (<<document-allocators-outside>>): it asks the document's
allocator for nothing, and its failure is the standard allocator's `std::bad_alloc`. A program that
must not meet one, or that keeps its text in memory of its own, writes to a sink.

[#document-stringify-to]
=== In pieces, to a sink

`wd::stringify_to(v, sink, indent, chunk)` writes the same bytes as `stringify`, in pieces of at
most `chunk` bytes, 4096 unless told otherwise, to a sink: any callable that takes a
`std::string_view` and returns `void` or `wd::result<void>`. A failure the sink returns stops the
writing and is returned; an exception it throws propagates. The document is unchanged either way,
and a writer holds no recursion, so a document nested as deep as memory allows is written:

[source]
----
include::{examples}/document_streaming.cpp[tag=stringify_to,indent=0]
----

[listing]
----
include::{examples}/document_streaming.expected[lines=12..13]
----

The first sink writes a bar after each piece of 8 bytes; the second keeps the first piece, then
fails, which stops the writing there.

`stringify_to` keeps its stack, which takes the place of recursion, and the chunk it has not yet
handed to the sink in room of its own, 16 levels of the stack and 4096 bytes of the chunk, and
allocates only past them, in the document's allocator (<<document-allocators>>): a value nested 16
deep or less, written in chunks of at most 4096 bytes, allocates nothing. With exceptions, an
allocator that has no room for them is `errc::capacity`, which stops the writing as a sink's failure
does. A sink that appends to a string of the program's choosing, a
`std::pmr::string` among them, keeps the text in memory the program chooses
(<<document-allocators-resource>>).

[#document-stringify-quote]
=== A string alone, quoted

`wd::quote(text, out)` is `JSON.stringify` of a string alone: it appends the string to `out` as a
JSON string literal, its quotes included, with the bytes `stringify` writes of the same string,
from the same code. `out` is a string of the program's own, a `std::string`, a `std::pmr::string`
or any type with `append(const char*, std::size_t)`, and the only thing that allocates, so a JSON
text of a fixed shape is written field by field into memory the program chooses, without a
document:

[source]
----
include::{examples}/document_streaming.cpp[tag=quote,indent=0]
----

[listing]
----
include::{examples}/document_streaming.expected[lines=14..15]
----

Text in a `std::string_view` is UTF-8, which `quote` checks: text that is not UTF-8, which no
JavaScript string is, returns `wd::errc::type` and leaves `out` as it was, as the last line shows,
which is {cpp}'s alone. Text in a `std::u16string_view` is UTF-16, any sequence of code units, with a
lone surrogate written as `\u` and its four lowercase hex digits, as JavaScript writes it since
ES2019; that overload has no failure of its own, and returns nothing.
