[#document-images]
== Images

A document lives in one block of memory, its image: a header of 64 bytes, then a heap that holds
the tree, its nodes, its indices and its strings. Every pointer inside is an offset from where it
is stored, and every size a 64-bit integer, so the image works at any 16-aligned address and has
the same bytes on a 64-bit native target and on wasm32. A document can therefore live in memory
it does not own, such as a browser's, be copied as bytes, be written to a file and read back, and
travel as binary between a program's processes. This section teaches the image itself: its bytes,
its header, what opening refuses, where it lives and how its size is managed. <<document-wire>>
sends images over streams and <<document-sharing>> shares them between threads and processes.

[#document-images-bytes]
=== The bytes

`wd::from_image(bytes)` copies an image into a new owned document, from any address;
`doc.clone()` does the same with a document's own:

The same operations give the same image, byte for byte, at any address and on every target: the
digest above is the one every target of webcpp's continuous integration prints, natively with
Clang and GCC, on emscripten, and on wasm32-wasip2 and wasm32-wasip3. Free memory is zero: a
buffer is zeroed when it is made or grown, a block is zeroed before it is freed, and nodes are
built in place. So an erased value, a secret among them, leaves none of its bytes in the image,
and the image is a function of the operations alone.

After an operation that failed for want of room, the document's content is as it was, but bytes
of the heap's free space may differ, where the heap keeps its own bookkeeping: compare documents
with `==`, not their raw images, after a failure.

[#document-images-header]
=== The header

The header says what the bytes after it are, in the byte order of the machine that wrote it:

[cols="1,1,3",options="header"]
|===
| Offset | Size | Field

| 0 | 8 | the magic, `WCPPDOC` and a zero byte
| 8 | 4 | the format version, 1
| 12 | 4 | the byte-order mark, `0x01020304` as the writer's machine writes it
| 16 | 4 | reserved, zero; an image whose reserved bytes are not zero is refused
| 20 | 4 | the layout tag: a hash of the sizes and alignments of the tree's node, its container and the heap, and of the traits (<<document-traits-identity>>)
| 24 | 8 | the size of the image
| 32 | 8 | the offset of the tree's container, the heap's first block, the same in every image
| 40 | 8 | the id the next node takes; ids are never reused
| 48 | 8 | the seal: zero for an image that is not sealed, else the high bit and the CRC-32C of the image, with these eight bytes taken as zero (<<document-wire-sealed>>)
| 56 | 8 | zero
|===

The format version is the library's: `webcpp::document::format_version`, which the library raises when
the layout of an image changes, and then provides a migration from the previous version. The Boost
release an image was written with is not in the header, and a Boost upgrade does not change the
version, since the structures the image holds, Boost.Interprocess's `rbtree_best_fit` blocks and
Boost.MultiIndex's ordered index nodes, rarely change. The library watches them: its format test
compares the compact image of a fixed document, under each traits, with golden images committed with
the tests, and fails when a Boost release changes one byte of them. The bytes at offset 16 are kept
for a future version.

[#document-images-refused]
=== What is refused

`wd::open` and `wd::from_image` refuse bytes shorter than the header or than the size it states,
and another magic, with `errc::not_a_document`; and an image of another format version, byte order,
layout tag or nonzero reserved bytes, with `errc::incompatible_document`. A mismatch is refused,
never read or converted. Then the heap's own check of its structure runs, and a container offset other than
the heap's first block, or a pointer to the root that leaves the image, is `errc::not_a_document`
too, refused before anything is read through it. A sealed image whose bytes do not match its seal is
`errc::damaged_document`, and is checked first of all (<<document-wire-sealed>>).

changed by accident and is not authentication: *never open an image from a source you do not trust.*

[#document-images-storage]
=== Owned and external storage

A document's second template parameter is its storage:

[cols="1,2,3",options="header"]
|===
| Storage | The buffer | When it is full

| `wd::owned`, the default
| the document's own, 16-aligned
| it grows: a buffer twice the size, or what the operation needs if more, the image copied and the
  heap grown, up to the `max_bytes` of `create` or `from_image`, 1 GiB unless told otherwise; past
  it, `errc::capacity`

| `wd::external`
| a `std::span<std::byte>` its user owns and keeps alive, such as a browser's memory, 16-aligned
| the operation returns `errc::capacity` and changes nothing
|===

`wd::format(buffer)` makes a new, empty document in a buffer, holding `null`; `wd::open(buffer)`
opens the image a buffer holds, in place; `wd::parse_into(buffer, text)` parses into one. Every
operation finds its room before it allocates, so a full buffer is an error value, never a
half-made change. A buffer that is not 16-aligned is `errc::capacity` to `format`, which finds no
room for an image there, and `errc::not_a_document` to `open`.

[#document-images-reserve]
=== Reserving

A document that is to be built large grows by doubling: each time the image is full, a buffer twice
the size is made, the image is copied into it and the old one is freed. `reserve(bytes)` is
`std::vector::reserve` for an image: it makes the image hold at least `bytes` in one step, so that a
batch of insertions of a known size moves nothing, and `capacity()` says how large the image is. A
reservation moves the image once, which invalidates every `std::string_view` read from a value but no
handle or iterator, and clears a seal; a reservation within the capacity changes nothing. A request
past the document's `max_bytes`, or past an external image's size, is `errc::capacity` and changes
nothing.

[#document-images-shrink]
=== Shrinking

A document that is parsed starts at 4096 bytes, and a document that is built grows from there as it
needs. `doc.shrink_to_fit()` gives back the free space at the end of an owned image, and only that:
blocks are never moved, so a value that sits at the end of the heap keeps the image as large as its
end. For a small document it is the whole story, a few values shrinking to little more than a
kilobyte. For a document that grew and then let its values go, it may leave an image nearly as large
as it was, and a deep copy into a new document packs the content, as `compact` does in place
(<<document-images-compact>>):

[#document-images-compact]
=== Compacting

`doc.compact()` rebuilds an owned image as the compact image of its content: the nodes in document
order, their ids numbered from the first, each block right after the last with no hole between, and
the image exactly as large as they are. Where `shrink_to_fit` can only trim the free tail,
`compact` takes out every hole, so a document that lost most of its values is smaller compacted
than shrunk. Measured, the same on a 64-bit target and on wasm32: a small document of 60 members
after 54 of them were erased is 15,312 bytes after `shrink_to_fit` and 2,352 after `compact`; a
large one, with 90% of its members erased, is 2,080,304 bytes and 209,424.

Compacting also makes the image a function of the content alone. Two documents of equal content
have byte-identical images after it, whatever edits made them, whether they were parsed, or built by
`set`, `erase` and `splice`, or had values replaced; and a compact image compacts to itself. Equal
documents can then be compared, hashed or stored by their bytes, and a seal over a compact image is
the same everywhere.

`compact_size()` is the exact size of the compact image, which it reads from the nodes without
allocating anything, so a program sizes a block with it before it builds the image.
`compact_into(buffer)` writes the compact image into a 16-aligned buffer of the program's own and
opens it there, as an external document, zeroing the rest of the buffer and leaving the document as it was: it is the way to compact a
document that cannot reallocate, such as one leased from a pool or held in a shared block, or to send
an image without waste. It is `errc::capacity` for a buffer that is smaller than `compact_size()` or
not aligned, and writes nothing then.

Compacting removes holes, not the 192 bytes of each node (<<document-parsing-memory>>), so it does
not change how an image compares in size with the JSON text of the same document
(<<document-benchmarks-wire>>).

`compact()` builds the new image before it replaces the old one, so a failure changes nothing. As a
vector's reallocation does, it invalidates every handle, every `std::string_view` read from a value
and every iterator, and, the bytes having changed, it clears a seal: sealing again is the caller's.
The image's size afterwards is `compact_size()`, which is also its `capacity()`, so the next change
that needs room grows it.

A moved document takes the image of the one it is moved from, which then holds nothing: its
handles, and those of the document moved into, are invalid.
