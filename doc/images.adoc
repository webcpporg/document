[#document-images]
== Images

A document lives in one block of memory, its image: a header of 64 bytes, then a heap that holds
the tree, its nodes, its indices and its strings. Every pointer inside is an offset from where it
is stored, and every size a 64-bit integer, so the image works at any 16-aligned address and has
the same bytes on a 64-bit native target and on wasm32. A document can therefore live in memory
it does not own, such as a browser's, be copied as bytes, be written to a file and read back, and
travel as binary between a program's processes.

[#document-images-bytes]
=== The bytes

`doc.image()` is the image, a `std::span<const std::byte>` valid until the document's next change.
`wd::from_image(bytes)` copies an image into a new owned document, from any address;
`doc.clone()` does the same with a document's own:

The same operations give the same image, byte for byte, at any address and on every target: the
digest above is the one every target of webcpp's continuous integration prints, natively with
Clang and GCC, on emscripten, and on wasm32-wasip2 and wasm32-wasip3. Free memory is zero: a
buffer is zeroed when it is made or grown, a block is zeroed before it is freed, and nodes are
built in place. So an erased value, a secret among them, leaves none of its bytes in the image,
and the image is a function of the operations alone.

After an operation that failed for want of room, the document's content is as it was, but bytes
of the heap's free space may differ, where the heap keeps its own bookkeeping: compare documents
with `==`, not their raw images, after a failure.

[#document-images-header]
=== The header

The header says what the bytes after it are, in the byte order of the machine that wrote it:

[cols="1,1,3",options="header"]
|===
| Offset | Size | Field

| 0 | 8 | the magic, `WCPPDOC` and a zero byte
| 8 | 4 | the format version, 1
| 12 | 4 | the byte-order mark, `0x01020304` as the writer's machine writes it
| 16 | 4 | the `BOOST_VERSION` of the writer
| 20 | 4 | the layout tag: a hash of the sizes and alignments of the tree's node, its container and the heap, and of the traits (<<document-traits-identity>>)
| 24 | 8 | the size of the image
| 32 | 8 | the offset of the tree's container, the heap's first block, the same in every image
| 40 | 8 | the id the next node takes; ids are never reused
| 48 | 16 | zero
|===

[#document-images-refused]
=== What is refused

`wd::open` and `wd::from_image` refuse bytes shorter than the header or than the size it states,
and another magic, with `errc::not_a_document`; and an image of another format version, byte order,
Boost version or layout tag, with `errc::incompatible_document`. A mismatch is refused, never read
or converted. Then the heap's own check of its structure runs, and a container offset other than
the heap's first block, or a pointer to the root that leaves the image, is `errc::not_a_document`
too, refused before anything is read through it.

*An image is trusted input.* Those checks cannot prove sound every offset inside the tree, so an
image travels only between a program's own processes and peers it trusts; untrusted data enters as
JSON text, which the parser checks entirely.

[#document-images-storage]
=== Owned and external storage

A document's second template parameter is its storage:

[cols="1,2,3",options="header"]
|===
| Storage | The buffer | When it is full

| `wd::owned`, the default
| the document's own, 16-aligned
| it grows: a buffer twice the size, or what the operation needs if more, the image copied and the
  heap grown, up to the `max_bytes` of `create` or `from_image`, 1 GiB unless told otherwise; past
  it, `errc::capacity`

| `wd::external`
| a `std::span<std::byte>` its user owns and keeps alive, such as a browser's memory, 16-aligned
| the operation returns `errc::capacity` and changes nothing
|===

`wd::format(buffer)` makes a new, empty document in a buffer, holding `null`; `wd::open(buffer)`
opens the image a buffer holds, in place; `wd::parse_into(buffer, text)` parses into one. Every
operation finds its room before it allocates, so a full buffer is an error value, never a
half-made change. A buffer that is not 16-aligned is `errc::capacity` to `format`, which finds no
room for an image there, and `errc::not_a_document` to `open`.

=== Shrinking

moved, so a value that sits at the end of the heap keeps the image as large as its end; a deep copy

handles, and those of the document moved into, are invalid.
